# 台北市公車即時回報地圖 App — 需求規格

> 來源：2026-07-31 需求訪談
> 狀態：已確認（含設計階段 5 項決策修正）

## 1. 產品定位

iOS App，聚焦**台北市公車**。

- **主功能**：地圖即時顯示公車位置（資料來源：交通部 TDX）
- **輔助功能**：匿名群眾回報公車狀況，並與 TDX 官方資料交叉比對
- **核心差異化**：官方 App 與 Google Maps 缺乏的 ①群眾即時回報 ②地圖視覺化。
  其中「**使用者回報與官方預估不符**」的警示，是官方管道給不了的資訊。

## 2. 範圍

- 僅台北市公車路線（`City=Taipei`），不含新北市
- 擴充雙北列為 MVP 後續事項

## 3. 即時性

- 後端每 15 秒拉取 TDX 動態資料
- 需求方要求誤差 ≤ 30 秒
- ⚠️ **已知限制**：TDX 動態資料官方更新頻率為每分鐘，端到端誤差最壞情況會超過 30 秒。
  對策為 UI 顯示每筆資料的實際時間戳（「N 秒前」），詳見 `DESIGN.md` §0.1。

## 4. 群眾回報

### 4.1 回報類型

| 類型 | 內容 | 可與官方資料比對？ |
|---|---|---|
| 誤點／尚未出現 | — | ✅ 與 TDX N1 `EstimateTime` 比對 |
| 車廂擁擠度 | 有位／站位／爆滿 | ❌ **TDX 無任何載客/擁擠度欄位（已查證）**，純群眾資料 |
| 站牌異常 | 牌面錯誤、施工封閉等 | — |

> 查證結論：台北市公車無公開的車廂感測器／監視器擁擠度資料，
> TDX 動態資料僅含 A1（GPS 位置）、A2（到離站）、N1（預估到站）。
> 擁擠度回報須在 UI 標示「僅供參考，未經官方驗證」。

### 4.2 回報內容

- 文字說明：**選填**（≤ 100 字）
- ~~照片：選填~~ → **延後至 v1.1**（決策 D5，理由見 §8）

### 4.3 身分

- 匿名、**免登入**（使用者無需輸入任何資訊、看不到任何登入畫面）
- 技術上使用 **Firebase Anonymous Auth** 取得可驗證身分，使用者全程無感（決策 D3）

### 4.4 防濫用

| 機制 | 參數 |
|---|---|
| 裝置頻率限制 | 同裝置（IDFV）對同一站牌／路線 **2 分鐘**內限回報一次 |
| 位置驗證 | 使用者需位於站牌 **150 公尺**內才能送出 |
| 身分驗證 | Firebase Anonymous Auth + App Check（決策 D3）|
| 伺服器端執行 | 上述檢查**一律在 Cloud Functions 執行**，client 不得直接寫入資料庫 |
| 檢舉機制 | 使用者檢舉達門檻自動隱藏 |
| 人工審核 | **不做**（一人開發，無人力）|

> 150 公尺（而非 500 公尺）的理由：台北市部分站牌間距極近，500 公尺會涵蓋錯誤站牌。

### 4.5 生命週期

- 地圖顯示：回報後 **10 分鐘**自動失效
- 即時層：Firestore 僅保留 10 分鐘熱資料（TTL 自動清理）
- 歷史層：每筆回報同步串流至 **BigQuery 永久留存**，供未來 AI 分析（決策 D2）

### 4.6 我的回報與刪除權（決策 D6）

為履行個資法的當事人刪除權，同時不引入帳號系統：

- App **本機**保存自己送出的回報摘要（`reportId` 等），**不上傳**
- 「我的回報」畫面可查看與刪除
- 刪除時以「本機清單 + Firebase 匿名 uid」雙重驗證所有權
- Firestore 熱資料立即刪除；**BigQuery 歷史資料以佇列 + 每日排程批次刪除**
  （streaming buffer 限制使即時刪除不可行，見 DESIGN.md §4.4）
- UI 文案必須為「已受理刪除，24 小時內完成」，**不可寫「已刪除」**
- **已知限制**：刪除 App 後重裝會取得新的匿名 uid，先前回報將無法再刪除

## 5. UI/UX

- 地圖**簡潔**為主，不做複雜多線路網視覺化（明確排除類似「軌島」的路網呈現密度）
- **預設畫面**（未選路線）：自動定位，顯示附近所有路線公車，以小型路線號碼標籤呈現，
  上限 60 台；視野 > 3 公里時自動隱藏公車，只留站點聚合標記（決策 D4）
- **選定路線後**：只顯示該路線的公車、站牌與路線線型（乾淨模式）
- 可用路線號碼搜尋並篩選
- 回報流程：點站牌 → 選類型 → （選填文字）→ 送出
- 每個公車標記顯示資料時間戳（「N 秒前」），> 90 秒標示「訊號中斷」

## 6. 技術決策

| 項目 | 決策 |
|---|---|
| UI 框架 | SwiftUI |
| 地圖 | Apple MapKit（免費、無用量限制、原生體驗）|
| 最低 iOS 版本 | **iOS 18+** |
| 後端 | Firebase（現成 BaaS，不自架伺服器）+ Cloud Run（TDX proxy）|
| 即時位置傳輸 | HTTPS 輪詢 15s + CDN 快取，**不用** Firestore listener（決策 D1）|
| 資料源 | 交通部 TDX（金鑰僅存於後端，**絕不打包進 App**）|

## 8. 明確排除於 MVP（未來待開發）

1. **照片上傳與內容審核**（決策 D5）
   排除理由：直接開發約 1 週；Cloud Vision 是唯一可能失控的帳單項目；
   UGC 會顯著提高 App Store 首次送審退件風險；
   對核心價值（誤點交叉比對）貢獻最小，該功能依賴結構化資料而非照片。
2. 帳號系統（可見的登入註冊功能）
3. 我的最愛路線
4. 個人化推播（如「你關注的路線誤點了」）
5. **GPS 速度偵測「智慧判斷搭乘中」自動詢問擁擠度**
   （原構想：App 開啟時監控裝置 GPS，連續 30 秒速度 > 25km/h 即彈窗詢問擁擠度，
   並比對附近公車車牌讓使用者確認搭乘班次。
   排除理由：需持續前景定位造成耗電、速度單一條件誤判率高
   （下坡單車／捷運／自小客車皆會觸發）、車牌比對需開發軌跡比對演算法，
   複雜度超出 2 個月 MVP 範圍。）
6. 擴充至新北市／雙北
